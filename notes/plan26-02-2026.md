# Plan: Migrate API from Python/Flask to Java/Spring (Strangler Pattern)

## Problem

Current backend is Python/Flask with DDD/Clean Architecture, Celery+Redis async jobs, SQLAlchemy, and Pydantic contracts.
New challenge: migrate to Java stack (Spring Boot, Spring Data JPA, Spring AI, Spring Security, Maven) while preserving production behavior.

## Confirmed Constraints

- Migration strategy: **Strangler** (gradual replacement).
- Compatibility target: **100% existing API contract compatibility** for current web app.
- Infrastructure: **keep current infra first** (PostgreSQL, Redis/queue topology, deployment shape).
- Java baseline: **Java 21 LTS**.
- Java code location: **`/api-java`** (new top-level directory alongside `/api`).
- Schema migration tool: **Flyway**.
- Build tooling: **Maven** (system `mvn 3.8.7`; Maven Wrapper `mvnw` included but broken/slow — use system Maven).
- Spring Boot version: **3.4.x** (latest stable compatible with Java 21).

### Authentication Architecture

- **Flask-Login** with custom `request_loader` dispatching by blueprint name.
- **PassportService**: JWT HS256 tokens using `SECRET_KEY` — issues/verifies tokens for console and web.
- **Console auth**: Token → decode `user_id` → `AccountService.load_logged_in_account()` → sets tenant context.
- **Service API auth**: `Authorization: Bearer <api_token>` → Redis-cached `ApiToken` lookup → App/Tenant validation.
- **Web auth**: JWT passport → `end_user_id` → EndUser lookup; enterprise path adds SSO/WebApp auth checks.
- **Admin API key**: Optional header-based admin key matching (`X-WORKSPACE-ID` + admin key).
- **RBAC roles**: `owner`, `admin`, `editor`, `normal`, `dataset_operator` via `TenantAccountRole`.
- **Decorators (22 in `wraps.py`)**: `setup_required`, `account_initialization_required`, `enterprise_license_required`, `cloud_edition_billing_*` (4 variants), `edit_permission_required`, `is_admin_or_owner_required`, edition guards (`only_edition_*`), feature gates (`email_*_enabled`, `enable_change_email`, `is_allow_transfer_owner`, `knowledge_pipeline_publish_enabled`), rate limiters (`annotation_import_rate_limit`, `annotation_import_concurrency_limit`), decryptors (`decrypt_password_field`, `decrypt_code_field`), `cloud_utm_record`.

### Module Dependency Rules

```
dify-api-boot → dify-api-gateway → dify-{domain modules} → dify-common
                                  → dify-worker
```

- `dify-common`: Zero Spring dependencies. POJOs, error codes, shared constants, utility classes.
- `dify-{domain}`: Spring Data JPA entities, repositories, service classes. No web/controller dependencies.
- `dify-api-gateway`: Spring Web controllers, security config, CORS, exception handlers. Depends on domain modules.
- `dify-worker`: Async task processors. Depends on domain modules. No web dependencies.
- `dify-api-boot`: Assembles everything. Contains `@SpringBootApplication`, `application.yml`, Flyway migrations.

## Error Envelope Parity

Python pattern:

```python
class BaseHTTPException(HTTPException):
    error_code: str = "unknown"
    data = {"code": self.error_code, "message": self.description, "status": self.code}
```

Java equivalent in `dify-common`:

```java
public class DifyApiException extends RuntimeException {
    private final String errorCode;
    private final int httpStatus;
    // ...
}

// Response body (Jackson serialization):
public record ErrorResponse(String code, String message, int status) {}
```

Spring `@ControllerAdvice` in `dify-api-gateway` maps `DifyApiException` → `ErrorResponse` JSON.

## Auth Parity Mapping

| Python Mechanism                   | Java Equivalent                                                            |
| ---------------------------------- | -------------------------------------------------------------------------- |
| `PassportService.issue/verify`     | `JwtTokenService` using same HS256 + `SECRET_KEY`                          |
| `flask_login.request_loader`       | Spring Security `OncePerRequestFilter` chain                               |
| Blueprint-based auth dispatch      | Security filter chain per URL pattern (`/console/**`, `/v1/**`, `/api/**`) |
| `ApiToken` Redis cache + DB lookup | `ApiTokenService` with Spring Data Redis + JPA                             |
| `@setup_required`                  | Custom Spring Security filter or `HandlerInterceptor`                      |
| `@account_initialization_required` | Method security or interceptor                                             |
| `@cloud_edition_billing_*`         | AOP aspect or interceptor                                                  |
| `@edit_permission_required`        | `@PreAuthorize` with custom SpEL expression                                |
| `TenantAccountRole` RBAC           | Spring Security `GrantedAuthority` hierarchy                               |
| Admin API key header               | Dedicated filter in security chain                                         |

### Critical: Shared JWT Secret

Both Python and Java services **must** use the same `SECRET_KEY` for JWT HS256 so tokens issued by either stack are valid during the dual-stack period. This is the core interoperability requirement.

## Celery → Spring Worker Mapping

| Python (Celery)                           | Java (Spring)                                              |
| ----------------------------------------- | ---------------------------------------------------------- |
| `@celery.task` decorator                  | `@Component` service with `@Async` or Redis listener       |
| `task.delay()` / `task.apply_async()`     | `RedisTemplate.convertAndSend()` or `StreamOperations`     |
| Celery broker (Redis)                     | Same Redis instance, compatible queue format or new queues |
| Celery beat (scheduled)                   | `@Scheduled` + ShedLock for distributed locking            |
| `FlaskTask.__call__` (app context)        | Spring ApplicationContext is always available              |
| Task retries (`max_retries`, `countdown`) | Spring Retry (`@Retryable`) or manual retry logic          |
| Queue selection (`queue=`)                | Redis Stream groups or dedicated listener containers       |

### Strategy During Dual-Stack Period

- **Option A (Recommended)**: Java workers consume from **new** Redis queues/streams. Python Celery keeps its existing queues. The gateway/controller layer decides which queue to publish to based on which stack owns the slice.
- **Option B**: Java workers consume from Celery-compatible Redis queues (requires Celery message format compatibility — complex and fragile).

## Cross-Cutting Guardrails

### Contract Tests

- Python vs Java golden tests must pass before any endpoint cutover.
- Use stored request/response pairs from production traffic (sanitized) as test fixtures.
- Automated CI job comparing Python and Java responses for the same inputs.

### Data Safety

- **No schema-breaking changes** without backward-compatible Flyway migration.
- Java Flyway and Python Alembic must not conflict — use separate migration version namespaces or coordinate version ordering.
- During dual-stack: both stacks connect to the same database instance (read/write).
- **Critical**: Both stacks must handle concurrent writes to shared tables correctly. Use optimistic locking (`@Version` / row versions) where applicable.

### Observability Parity

- Trace IDs: Java OTEL agent must propagate same `X-Trace-Id` / `X-Span-Id` headers.
- Log format: Match Python log format for dashboard compatibility.
- Metrics: Same metric names/labels for existing dashboards (Prometheus/Grafana).

### Security Parity

- JWT tokens cross-compatible (shared `SECRET_KEY`, same HS256 algorithm).
- CORS policies identical per-path.
- CSRF token handling matched.
- RBAC decisions produce identical allow/deny for same user+action+resource.
- Rate limiting behavior equivalent (Redis ZSET patterns matched).

## Risks & Mitigations

| Risk                                              | Likelihood              | Impact   | Mitigation                                                                                                                                                                                                      |
| ------------------------------------------------- | ----------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hidden behavioral coupling in Python services     | High                    | High     | Shadow traffic + snapshot tests + explicit invariants                                                                                                                                                           |

## Post-TODO #5 Review: Required Modifications to the Plan

> Review performed 2026-02-27 after Slice 1 (Console Bootstrap) completion. Assesses impact on all remaining work.

### 1A. CRITICAL — `/console/api/system-features` Mixed Auth Pattern (Slice 2 Blocker)

**Problem**: SecurityConfig already places `/console/api/system-features` in the **bootstrap filter chain (Order 2, `permitAll()`)**. The JWT filter does NOT execute for this chain, so `SecurityContextHolder` is always empty — the Java endpoint cannot distinguish authenticated from unauthenticated callers.

**Python behavior** (`controllers/console/feature.py:52-59`):

```python
try:
    is_authenticated = current_user.is_authenticated
except Unauthorized:
    is_authenticated = False
return FeatureService.get_system_features(is_authenticated=is_authenticated).model_dump()
```

When authenticated **and `ENTERPRISE_ENABLED` is true**, Python returns license details (`license.status`, `license.expired_at`, workspace limits) via `_fulfill_params_from_enterprise(system_features, is_authenticated)`. When unauthenticated (or when `ENTERPRISE_ENABLED` is false), those fields return defaults/empty values.

> **Nuance for SELF_HOSTED**: In SELF_HOSTED edition (where `ENTERPRISE_ENABLED` is `False`), the `is_authenticated` flag has **zero effect** on the response — the enterprise block in `get_system_features()` never executes. This makes the OptionalJwtFilter technically unnecessary for SELF_HOSTED. However, implementing it is still recommended for correctness, forward-compatibility with enterprise, and to avoid subtle behavioral drift if `ENTERPRISE_ENABLED` is later turned on.

**Required fix — implement one of**:

- **(Recommended) Option A**: Add a custom `OptionalJwtFilter` (extends `OncePerRequestFilter`) to the bootstrap filter chain that reads the JWT `Authorization` header if present, validates it, and populates `SecurityContext` — but **never rejects** if the token is missing or invalid. This matches the Python try/catch pattern exactly.
- **Option B**: Move `/console/api/system-features` to the console chain (Order 3) but configure `JwtAuthenticationFilter` to be non-rejecting for that specific path (adds complexity to the filter).
- **Option C**: Create a separate `@Order(2)` filter chain just for `/console/api/system-features` with optional JWT, keep the other bootstrap paths in a simpler `permitAll` chain.

**Impact**: Must be resolved before Slice 2 implementation begins. Affects `SecurityConfig.java` and may require a new filter class in `dify-api-gateway`.

**Status**: Existing risk entry `system-features mixed auth pattern` upgraded from "Low likelihood" to **Confirmed — requires SecurityConfig modification**.

### 1B. Cross-Cutting Concern — `@setup_required` Not Generalized

**Problem**: In Python, `@setup_required` (`wraps.py:217-232`) is a decorator applied to most console endpoints. It has **two branches** (not one):

1. If `EDITION == "SELF_HOSTED"` AND `INIT_PASSWORD` env var is set AND `DifySetup` not found → raises `NotInitValidateError` (401, `not_init_validated`)
2. If `EDITION == "SELF_HOSTED"` AND `DifySetup` not found (no INIT_PASSWORD) → raises `NotSetupError` (401, `not_setup`)

In TODO #5, setup checking is only done **inside** `SetupController.getSetupStatus()` itself. It is not enforced as a cross-cutting filter.

Slice 2's `/console/api/features` endpoint uses `@setup_required`, and every subsequent console slice (3–10) will also need it.

**Required fix**: Implement a `SetupRequiredInterceptor` (`HandlerInterceptor`) or `SetupRequiredFilter` registered on the console filter chain (Order 3). Should:

- Query `DifySetupRepository.count() > 0` (cache result in Redis — setup status rarely changes, 5-minute TTL).
- **Two-branch error**: If `dify.init-password` is configured and setup not complete → return `{"code": "not_init_validated", "message": "...", "status": 401}`. If no init-password and setup not complete → return `{"code": "not_setup", "message": "...", "status": 401}`. This matches the Python decorator exactly.
- Exclude bootstrap paths (they're in a separate chain, so this is automatic).
- Note: Python reads `INIT_PASSWORD` via `os.environ.get("INIT_PASSWORD")` directly; Java must read from `DifyProperties.getInitPassword()` to honour the config-binding convention.

**Impact**: Must be implemented as a **Slice 2 prerequisite**. Affects `dify-api-gateway` (new interceptor) and `SecurityConfig.java` (interceptor registration).

### 1C. Cross-Cutting Concern — `@account_initialization_required` Not Planned

**Required fix**: Implement `AccountInitializationInterceptor` that:

**Impact**: Slice 2 prerequisite. Should be implemented alongside `SetupRequiredInterceptor` for consistency.
